## 한 장 요약

**진단** — 오케스트레이션 엔진은 완성도가 높으나(정의 체계·부작용 등급·인용 무결성·설정 동결),
데이터 연결 계층은 PostgreSQL 1종 + 문서 7종 + 폴더 읽기에 머물러 있고 셋이 서로 통합되어
있지 않으며 접근 권한과 감사가 사실상 없다.

**핵심 통찰** — 현재 데이터는 `db.query` / `knowledge.*` / `file.read` 세 갈래로 따로 흐르며
공통 메타데이터·공통 권한·공통 감사 지점이 없다. 고도화의 본질은 커넥터를 더 만드는 것이
아니라 **이 셋을 하나의 데이터 연결 계층으로 통합**하는 것이다.

**우선순위 변경 제안** — 요청하신 순서(DB → 파일 → 문서 → 폴더 → API → 권한)에서
**권한·감사를 마지막에서 처음으로 옮겼다.** 관문 없이 만든 접근 경로는 나중에 다 못 막고
(현재 `POST /data-sources/query`가 정확히 그 사례), 권한·감사가 없으면 애초에 고객사가
DB 접속정보를 주지 않아 검증할 실데이터를 못 얻는다.

**로드맵**

| Phase | 목표 | 핵심 산출 |
|---|---|---|
| 1. 신뢰 기반 | "회사 데이터를 붙여도 되는 시스템"이 된다 | 사용자·역할, DataAccessGateway, 정책 엔진, 감사 로그, 커넥터 프레임워크 |
| 2. 연결 확장 | 한국 중소 제조·물류 실데이터에 붙는다 | MSSQL·Oracle, 스키마 카탈로그, 엑셀·HWP, 비동기 인제스트, 폴더 증분동기화, 하이브리드 검색 |
| 3. 업무 통합 | 조회를 넘어 업무 흐름에 들어간다 | REST/OpenAPI 커넥터, 결재 연동, 감사 하네스, 대시보드, 프런트 재구조화 |

## 확정 필요 사항

착수 전에 답이 필요한 항목은 `02_PRODUCT_PLAN.md` 8절과 `03_CONNECTOR_DETAIL_DESIGN.md`
16절에 정리되어 있다. 가장 급한 셋:

1. **배포 모델** — 하이브리드 설계 / 온프레미스 1차 출시 권고안 채택 여부
2. **인증 방식** — 자체 계정 / AD·LDAP / 국내 SSO
3. **앵커 고객 1곳** — 실제 DB 종류와 문서 포맷 분포가 여기서 확정된다 (MSSQL vs Oracle 우선순위, HWP 비중)
