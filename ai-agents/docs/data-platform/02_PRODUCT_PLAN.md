## 1. 제품 정의

### 1.1 현재 (What it is)

> YAML로 구성한 멀티 에이전트 팀이 문서·개발·투자자문·영상 업무를 수행하는 개인/소규모 오케스트레이터.

### 1.2 목표 (What it should become)

> **회사의 DB·문서·폴더·API를 안전하게 연결하고, 사내 규정과 권한 아래에서 AI 에이전트 팀이 실제 업무를 수행하는 한국형 기업 AI 업무 플랫폼.**

### 1.3 전환의 본질

| 축 | As-Is | To-Be |
|---|---|---|
| 데이터 | 사용자가 붙여넣는 것 | **회사 시스템에 상시 연결된 것** |
| 사용자 | 단일 운영자 (API 키 1개) | 조직·부서·역할이 있는 다수 사용자 |
| 신뢰 | "결과가 그럴듯한가" | "누가 무엇을 근거로 했고 감사 가능한가" |
| 배포 | 개인 PC Docker | 고객사 온프레미스 / 관리형 |
| 확장 | Python 코드 수정 | **커넥터 정의(YAML) 추가** |

### 1.4 목표 고객

1. **1차 (앵커)** — 중소 제조·물류기업 (매출 100억~2,000억). 사내 DB·엑셀·HWP·PDF가 섞여 있고, IT 인력은 1~3명, 보안 요구는 높지만 예산은 제한적.
2. **2차** — 공공기관/공기업 산하 (HWP·폐쇄망 필수).
3. **3차** — 회계·법무·엔지니어링 등 문서 집약 전문 서비스업.

### 1.5 경쟁 포지셔닝

| 대안 | 강점 | 약점 | 본 제품의 차별점 |
|---|---|---|---|
| ChatGPT/Claude Enterprise | 모델 품질 | 사내 DB 미연결, 데이터 외부 유출 우려, 한국 문서 포맷 약함 | **온프레미스 + 사내 DB 직결 + HWP** |
| MS Copilot | Office 통합 | M365 종속, 국내 레거시 ERP 미연결, 고가 | **국내 ERP/그룹웨어 커넥터, 라이선스 종속 없음** |
| 국내 RAG 챗봇 SI 구축 | 맞춤 | 프로젝트마다 재개발, 유지보수 비용 | **정의(YAML) 기반 재사용, 제품화된 커넥터** |
| n8n/Dify 등 오픈소스 | 저렴 | 다중 에이전트 품질 통제·인용 무결성·승인 흐름 약함 | **품질 게이트·인용 계약·인간 승인이 코어에 내장** |

**핵심 차별화 3가지 (이미 코드에 있는 것을 상품 언어로)**

1. **인용 무결성** — AI가 지어낸 근거는 인용조차 못 한다 (`collaboration.py` 주장 계약).
2. **구조는 계약** — 회사 양식·시방서·테이블정의서를 LLM 없이 결정적으로 파싱해 산출물 골격을 강제.
3. **부작용 등급 + 인간 승인** — 읽기(L0)/산출물(L1)/샌드박스(L2)/외부영향(L3)을 워크플로 단위로 상한 설정.

## 2. 배포 모델 3안 비교 (미정 항목 의사결정용)

### 2.1 비교표

| 기준 | A. 온프레미스/폐쇄망 | B. 클라우드 SaaS | C. 하이브리드 |
|---|---|---|---|
| 데이터 위치 | 전부 고객사 | 전부 클라우드 | 데이터·커넥터 사내, LLM 추론만 외부 |
| LLM | 사내 GPU + sLM (Ollama) | 상용 API | 로컬 sLM + 프런티어 API 혼합 (슬롯 패턴) |
| 초기 구축 난이도 | 높음 (GPU 서버, 방화벽, 설치 지원) | 낮음 | 중간 |
| 단가/수익모델 | 구축비 + 연 유지보수 | 월 구독 (사용자당) | 구독 + 추론 사용량 |
| 품질 상한 | **제한적** (로컬 모델 한계) | 높음 | 높음 |
| 국내 제조업 수용성 | **가장 높음** | 낮음 (사내 데이터 외부 반출 거부감) | 중간 (규정에 따라 갈림) |
| 개발 비용 | 중 (설치·업데이트 배포 체계 필요) | **높음** (멀티테넌시, 과금, 운영) | 중 |
| 확장성(매출) | 낮음 (건별 SI화 위험) | **높음** | 중 |
| 현재 코드와의 거리 | **가깝다** (Docker Compose + Ollama 이미 지원) | 멀다 (테넌시·과금·SSO 전부 신설) | 가깝다 |

### 2.2 권고

**단계적 접근: C(하이브리드)를 기본 아키텍처로 설계하고, A(온프레미스)를 1차 상품으로 출시한다.**

근거:

1. 현재 코드는 이미 하이브리드 전제로 되어 있다 — `WorkspaceModelPolicy(local_only/hybrid/cloud_allowed)`와 슬롯 패턴이 그것이다. **새로 설계할 필요가 없다.**
2. 1차 고객(중소 제조·물류)은 사내 데이터 외부 반출에 강한 거부감이 있다. 온프레미스가 **영업 진입 조건**이다.
3. SaaS로 먼저 가면 멀티테넌시·과금·SSO·규정 대응에 6개월 이상을 쓰고 정작 데이터 커넥터는 못 만든다.
4. 단, **아키텍처는 처음부터 멀티테넌시를 부정하지 않게 짠다.** 구체적으로: 모든 데이터 테이블에 `tenant_id`(현 `workspace_id`를 승격)를 두고, 커넥터 자격증명을 DB에 암호화 저장하며(환경변수 탈피), 감사 로그를 테넌트 스코프로 남긴다. 이 셋만 지키면 나중에 B로 가는 비용이 재작성이 아니라 확장이 된다.

> **결정 요청 사항:** 이 권고를 채택하면 Phase 1의 인증 설계는 "사내 계정 + AD/LDAP 연동 가능 구조"로 가고, SaaS형 소셜 로그인·구독 과금은 범위 밖으로 뺀다.

## 3. 고도화 원칙

설계 전체를 관통하는 5개 원칙. 이후 모든 결정은 이 원칙으로 판정한다.

| # | 원칙 | 의미 |
|---|---|---|
| O-1 | **커넥터는 코드가 아니라 정의다** | 새 데이터 소스 추가는 YAML 정의 + 드라이버 플러그인 등록. 코어 수정 없음. 기존 "정의는 데이터" 원칙의 연장 |
| O-2 | **모든 데이터 접근은 단 하나의 관문을 통과한다** | DB·파일·폴더·API 무관하게 `DataAccessGateway` 1곳에서 권한 검사 + 감사 기록. 우회 경로를 만들지 않는다 |
| O-3 | **권한은 소스가 아니라 주체·객체·행위의 조합이다** | (사용자/역할) × (소스/스키마/테이블/컬럼/문서) × (read/query/export) |
| O-4 | **읽은 데이터는 명령이 아니라 증거다** | 기존 `injection_notice` 원칙을 전 커넥터에 확대. 외부에서 들어온 텍스트는 절대 지시로 해석하지 않는다 |
| O-5 | **연결은 실패를 전제로 설계한다** | 사내 DB는 죽고, 파일서버는 끊기고, API는 429를 뱉는다. 타임아웃·회로차단·재시도·부분성공을 기본값으로 |

## 5. 로드맵

전체 6개 항목을 **모두 설계**하고 3단계로 구현한다. 각 Phase는 그 자체로 고객에게 판매/시연 가능한 상태로 끝난다.

### Phase 1 — 신뢰 기반 (Trust Foundation)
> **목표: "회사 데이터를 붙여도 되는 시스템"이 된다.** 커넥터를 늘리기 전에 관문·권한·감사를 먼저 세운다.

| 항목 | 산출 |
|---|---|
| P1-1 | 사용자/조직/역할 모델 + 로그인 (기존 API 키는 서비스 계정으로 격하) |
| P1-2 | `DataAccessGateway` 신설 — 모든 데이터 접근 단일 관문화 |
| P1-3 | **권한 정책 엔진** (소스/스키마/테이블/컬럼 레벨 + 마스킹 규칙) |
| P1-4 | **데이터 접근 감사 로그** (`data_access_events`) + 조회 UI |
| P1-5 | `POST /data-sources/query` 권한 우회 차단 (As-Is Blocker) |
| P1-6 | 자격증명 저장소 — 환경변수 → DB 암호화 저장 (봉투 암호화) |
| P1-7 | **커넥터 프레임워크** — `ConnectorDefinition` YAML + 드라이버 레지스트리 |

**완료 판정:** 사용자 A는 생산 DB만, B는 회계 DB만 조회 가능하고, 주민번호 컬럼은 자동 마스킹되며, 모든 조회가 감사 화면에 남는다.

### Phase 2 — 데이터 연결 확장 (Connectivity)
> **목표: 한국 중소 제조·물류 기업의 실제 데이터에 붙는다.**

| 항목 | 산출 |
|---|---|
| P2-1 | **MSSQL 커넥터** (aioodbc/pymssql, T-SQL 전용 SQL 가드) |
| P2-2 | **Oracle 커넥터** (oracledb async, PL/SQL 가드) |
| P2-3 | **스키마 카탈로그** — 테이블/컬럼/코멘트/샘플값/관계 수집 + 한글 논리명 매핑 |
| P2-4 | **엑셀·CSV 표 인식 인제스트** — 시트/헤더/타입 추론 → 조회 가능한 테이블로 등록 |
| P2-5 | **HWP/HWPX 파서** + PPTX + 스캔 PDF OCR |
| P2-6 | **비동기 인제스트 파이프라인** — 큐, 진행률, 재시도, 중복 스킵 |
| P2-7 | **폴더 커넥터** — 인덱싱, 증분 동기화(mtime+hash), SMB/NAS 경로 |
| P2-8 | **하이브리드 검색** — BM25(한국어 형태소) + 벡터 + 리랭커 |

**완료 판정:** 고객사 MSSQL ERP + 공유폴더 엑셀·HWP 5,000건을 연결하고, "작년 3분기 A거래처 불량률 추이"에 근거 인용과 함께 답한다.

### Phase 3 — 업무 시스템 통합 (Integration)
> **목표: 조회를 넘어 업무 흐름에 들어간다.**

| 항목 | 산출 |
|---|---|
| P3-1 | **범용 REST/OpenAPI 커넥터** — 스펙 임포트, 인증(API Key/Bearer/OAuth2), 페이지네이션, 레이트리밋 |
| P3-2 | 국내 업무 시스템 커넥터 팩 (그룹웨어·전자결재·ERP 우선순위는 앵커 고객 확정 후) |
| P3-3 | 데이터 소스 접근 결재 워크플로 (민감 소스는 승인 후 조회, 기존 `human` 노드 재사용) |
| P3-4 | 감사 하네스 (CLAUDE.md 로드맵 2번) — 산출물 레지스트리 + 불변 이벤트 로그 + 드리프트 재검증 |
| P3-5 | 데이터 소스 상태 대시보드 (연결 상태, 동기화 지연, 실패율) |
| P3-6 | 프런트엔드 재구조화 (`App.tsx` 1,300 LOC 분해) |

**완료 판정:** 사내 그룹웨어 결재 문서와 ERP 데이터를 함께 근거로 삼아 보고서를 작성하고, 그 과정이 전부 감사 가능하다.

### 5.1 우선순위 판단 근거

사용자가 제시한 순서(DB → 파일 → 문서 → 폴더 → API → 권한)에서 **권한을 마지막이 아니라 처음으로 옮겼다.** 이유:

- 권한을 나중에 넣으면 이미 만들어진 커넥터 4종을 전부 다시 손봐야 한다. 관문 없이 만든 접근 경로는 나중에 절대 다 못 막는다 (현재 `POST /data-sources/query`가 정확히 그 사례다).
- 권한·감사가 없으면 **애초에 고객사가 자기 DB 접속정보를 주지 않는다.** Phase 2를 검증할 실데이터를 못 얻는다.
- 반대로 관문을 먼저 세우면 Phase 2의 커넥터 4종은 같은 인터페이스를 구현만 하면 되므로 개발이 오히려 빨라진다.

### 5.2 마일스톤 (상대 규모)

| Phase | 상대 공수 | 주요 리스크 |
|---|---|---|

| **개인정보보호법 위반** | 사업 중단급 | 컬럼 마스킹을 옵션이 아닌 기본값으로. 개인정보 컬럼 자동 탐지 + 기본 차단 후 명시적 허용 |
| **프롬프트 인젝션** | 사내 문서에 숨긴 지시로 데이터 유출 | 기존 `injection_notice` 원칙 전 커넥터 확대 + 도구 출력의 지시성 패턴 탐지 + L3 도구 기본 미등록 유지 |
| **DB 부하로 기간계 장애** | 고객사 신뢰 상실 | 읽기 전용 복제본 권장, 커넥션 상한, statement_timeout, 동시 질의 쿼터, 회로차단 |
