# 기능 확장 타당성 분석

세 계열(문서 종류·양식 추가 / 새 업무팀 / 입력 소스 확장)을 각각 판정한다.
판정 기준은 하나다: **"이걸 지금 하면 나중에 되돌려야 하는가?"**

결론부터:

| 계열 | 판정 | 이유 |
|---|---|---|
| ① 문서 종류·양식 추가 | 🟢 **지금 하세요** | 코드 변경이 거의 없음. 되돌릴 것도 없음 |
| ② 새 업무팀 추가 | 🟡 **1개만, 실사용 검증 후** | 유지보수 부채가 팀 수에 비례해 늘어남 |
| ③ 입력 소스 확장 | 🟡 **엑셀·HWP 읽기만** | 나머지는 권한 관문 전에 만들면 재작업 |

---

## ① 문서 종류·양식 추가 — 🟢 지금 하세요

### 왜 안전한가

이 시스템의 설계가 정확히 이걸 위해 만들어져 있습니다. `document-build-v1` 하나가
모든 문서 종류를 처리하고, 문서 성격은 **코드가 아니라 입력값**으로 결정됩니다.

```
새 문서 종류 추가 = --doc-type 문자열 변경
새 회사 양식 추가 = template/ 폴더에 파일 넣기
```

**코드 변경 0줄, 되돌릴 것 0개.** 위험이 없습니다.

### 난이도별 분류

| 하고 싶은 것 | 방법 | 난이도 | 코드 변경 |
|---|---|---|---|
| 새 문서 종류 (계약검토서, 회의록, 매뉴얼…) | `--doc-type` + `--instructions` | 즉시 | 없음 |
| 회사 양식 강제 | `template/` 에 파일 | 즉시 | 없음 |
| 자주 쓰는 조합 저장 | `.bat` 파일 또는 job_template YAML 추가 | 낮음 | 없음 (YAML만) |
| 출력에 Word(.docx) 추가 | `document.bundle` 에 포맷 추가 | 중간 | tools.py 소폭 |
| 출력에 한글(.hwp) 추가 | 신규 라이브러리 | 높음 | ⚠ 아래 참고 |

### 권장 순서

1. **doc_type 5~6개를 실제 업무로 돌려보세요.** 제안서·분석보고서·회의록·매뉴얼 등.
   여기서 "어떤 문서는 잘 되고 어떤 문서는 안 된다"가 드러납니다. 그게 다음 결정의 입력입니다.
2. 잘 되는 종류가 나오면 그걸 `examples/job_templates/*.yaml` 로 고정하세요.
   (버전 승급 규율 주의: 내용 바꾸면 `version` 필수 증가)
3. 출력 포맷 확장은 **그 다음**입니다.

### ⚠ HWP 출력에 대한 경고

읽기(파싱)와 쓰기(생성)는 난이도가 다릅니다. HWP **생성**은:

- 안정적인 오픈소스 라이브러리가 사실상 없습니다
- 한/글 자동화(COM)는 한/글이 설치된 Windows에서만 동작하고 서버 배포가 안 됩니다
- `pyhwp` 계열은 라이선스(GPL 계열) 검토가 필요합니다 — 상용화 시 법무 이슈

**현실적 대안:** Markdown → docx 로 내보내고, 한글에서 열어 저장. 지금은 여기까지가 합리적입니다.

## ② 새 업무팀 추가 — 🟡 1개만, 실사용 검증 후

### 기술적으로는 쉽습니다

```
examples/agents/<새역할>.yaml       ← 에이전트 정의
examples/teams/<새팀>.yaml          ← 팀 로스터 (슬롯 바인딩)
examples/workflows/<새워크플로>.yaml ← 파이프라인
examples/job_templates/<새잡>.yaml  ← 실행 프리셋
examples/preset_ui/<새UI>.yaml      ← UI 카드 (UI 쓸 경우)
```

전부 YAML입니다. 코드 변경 없습니다. **문서팀 워크플로를 복사해 에이전트 프롬프트만
바꾸면 절반은 끝납니다.**

### 그런데 왜 신중해야 하는가

**팀 수가 늘면 유지보수 부채가 선형으로 늘어납니다.** 지금 이미 4개 팀 / 에이전트 25개가
있고, 그중 **실사용 품질이 검증된 건 0개**입니다. 5번째 팀을 만들면 검증 안 된 게 5개가 됩니다.

앞선 사업성 분석에서 말씀드린 것과 같은 문제입니다. 혼자서 4개 팀을 유지하면서 데이터
플랫폼까지 만드는 건 불가능하고, 팀을 늘리면 그 계산이 더 나빠집니다.

### 판단 기준

새 팀을 만들기 전에 이 질문에 답하세요.

> **"이 팀이 만들 산출물을, 내가 이번 달에 실제로 3번 이상 쓸 일이 있는가?"**

- 예 → 만드세요. 실수요가 있는 도구는 만들 가치가 있습니다.
- 아니오 → 만들지 마세요. "있으면 좋을 것 같아서"는 부채만 남깁니다.

### 그래도 만든다면 — 추천 후보

앞선 분석에서 **"문서작성 + 소스분석 = 레거시 현대화 지원"**을 쐐기로 봤습니다.
그 가설을 강화하는 팀이라면 만들 가치가 있습니다.

| 후보 | 쐐기 가설과의 정합성 | 비고 |
|---|---|---|
| **견적·산정팀** (개발 공수 산정, 견적서) | 높음 — 소스분석 결과를 바로 받아 씀 | 문서팀 복제로 가능 |
| **계약·제안 검토팀** (RFP 분석, 요구사항 추출) | 높음 — 제안서 작업의 앞단 | `spec_parser` 재사용 가능 |
| 마케팅팀 | 낮음 | 범용 도구가 이미 잘함 |
| 인사·총무팀 | 낮음 | 수요 빈도 낮음 |

**하나만 고르세요.** 그리고 문서팀 실사용 검증(RTR 측정)이 끝난 다음에 하세요.
문서팀이 RTR 0.4를 못 넘기면 같은 구조로 만든 새 팀도 못 넘깁니다.

### 만들 때 지켜야 할 것

1. **기존 워크플로를 복사해서 시작.** `document_build.yaml` 이 협업·승인·인용 무결성을
   이미 다 갖고 있습니다. 처음부터 짜지 마세요.
2. **`version` 승급 규율.** 내용 바꾸면 반드시 version 증가. 안 그러면 `409 Conflict` 로 배포가 막힙니다.
3. **인용 무결성 계약을 빼지 마세요.** `require_evidence: true`, `evidence_path` 를 유지해야
   이 시스템의 유일한 차별점이 살아 있습니다.
4. **검증 시나리오를 같이 추가.** `verification/scenarios.py` 에 새 시나리오를 넣으면
   품질을 자동으로 잴 수 있습니다. 안 넣으면 또 검증 안 된 팀 하나가 늘어납니다.

## ③ 입력 소스 확장 — 🟡 엑셀·HWP 읽기만

### 계열을 둘로 나눠야 합니다

앞서 설계한 데이터 커넥터 계층(`docs/data-platform/03_...`)은 **Phase 1(권한·감사 관문)이
Phase 2(커넥터)보다 먼저**여야 한다고 판정했습니다. 그 이유는 관문 없이 만든 접근 경로는
나중에 다 못 막기 때문입니다.

**하지만 그 판정은 "회사 데이터를 연결하는 제품"에 대한 것이지, "내 파일을 읽는 개인 도구"에
대한 것이 아닙니다.** 둘은 다릅니다.

| 확장 | 지금 해도 되는가 | 이유 |
|---|---|---|
| **엑셀(.xlsx) 읽기** | 🟢 **하세요** | `extract_text()` 에 분기 하나 추가. 되돌릴 것 없음 |
| **HWP/HWPX 읽기** | 🟢 **하세요** | 동일. 한국형의 근간이고, 지금 없어서 실제로 불편함 |
| PPTX 읽기 | 🟢 해도 됨 | 동일, 난이도 낮음 |
| 스캔 PDF OCR | 🟡 나중 | 라이브러리 무겁고, 지금 병목이 아님 |
| 폴더 증분 색인 | 🟡 나중 | 파일 수가 수천 개를 넘을 때 필요 |
| **사내 DB 연결** | 🔴 **하지 마세요** | 권한 관문 없이 만들면 반드시 재작업 |
| **외부 API 연결** | 🔴 **하지 마세요** | 동일 |

### 엑셀·HWP 읽기를 지금 해도 되는 이유

이 둘은 **`app/knowledge.py` 의 `extract_text()` 에 분기를 추가하는 것**이 전부입니다.

```python
# app/knowledge.py — extract_text() 에 추가
if normalized_type in XLSX_TYPES:
    return _extract_xlsx(content)      # openpyxl, read_only=True, data_only=True
if normalized_type in HWPX_TYPES:
    return _extract_hwpx(content)      # zip + OWPML XML 파싱
```

- 권한 관문과 무관합니다 (이미 `APP_FILE_READ_ROOTS` 화이트리스트 안입니다)
- 나중에 커넥터 계층으로 옮길 때 **함수를 그대로 이동**하면 됩니다. 버리는 게 없습니다
- `FileReadService.read()` 도 같은 `extract_text()` 를 쓰므로 **폴더 읽기에 자동 반영**됩니다

### 구현 시 주의 — 조용한 실패 금지

현재 스캔 PDF는 pypdf가 빈 문자열을 반환해도 **조용히 빈 문서로 등록**됩니다(As-Is 분석 K-4).
엑셀·HWP를 추가할 때 같은 실수를 반복하지 마세요.

```python
MIN_EXTRACTED_CHARS = 50

text = extract_text(content, mime)
if len(text.strip()) < MIN_EXTRACTED_CHARS:
    raise ValueError(f"추출된 텍스트가 너무 짧습니다({len(text)}자). "
                     f"스캔 문서이거나 파싱에 실패했을 수 있습니다: {filename}")
```

### 엑셀은 "표"라는 것을 잊지 마세요

엑셀을 텍스트로 뭉개서 임베딩하면 **집계·필터 질의가 불가능**해집니다(As-Is 분석 K-3의 CSV 문제).
지금 단계에서는 텍스트 추출로 시작하되, 최소한 이렇게 하세요.

- 시트별로 분리
- 헤더 행을 인식해서 각 행을 `컬럼명: 값` 형태로 (열 위치가 아니라 이름으로 읽히게)
- 500행 넘으면 잘라내고 "N행 중 500행만 표시" 명시

나중에 표를 진짜 데이터셋으로 승격하는 건 커넥터 계층의 일입니다.

### HWP vs HWPX

**HWPX(.hwpx)부터 하세요.** ZIP + XML 구조라 파싱이 안정적입니다.
구형 HWP(.hwp) 바이너리는 실패율이 높고 라이선스 검토가 필요합니다.

실무 대응: 한/글에서 "다른 이름으로 저장 → HWPX"로 변환하는 절차를 안내하는 게
파서를 완벽하게 만드는 것보다 빠릅니다.

## 종합 — 권장 실행 순서

```
지금  ┌─ ① 문서 종류 5~6개를 실제 업무로 돌려본다        ← 코드 0줄
      │  (동시에) RTR 측정. verification/REWORK_PROTOCOL.md
      │
      ├─ ③ 엑셀 읽기 추가                                ← 함수 1개
      └─ ③ HWPX 읽기 추가                                ← 함수 1개

그다음 ┌─ RTR 결과를 보고 판단
      │   · 0.4 이하 → 쐐기 확인. ② 새 팀 1개 추가 검토
      │   · 0.4 초과 → 팀을 늘리지 말고 품질부터
      │
      └─ 출력 포맷(docx) 확장

나중  ┌─ 폴더 증분 색인 (파일 수천 개 넘을 때)
      └─ 데이터 커넥터 계층 (Phase 1 권한 관문부터)
```

**핵심:** ①과 ③의 읽기 확장은 **되돌릴 게 없어서** 지금 해도 손해가 없습니다.
②와 DB/API 연결은 **잘못 만들면 되돌려야 해서** 판단 근거(RTR)를 먼저 확보해야 합니다.

## 확장할 때 절대 건드리지 말 것

이 넷은 이 시스템의 차별점입니다. 확장하다가 편의를 위해 끄고 싶어질 텐데, 끄면 남는 게 없습니다.

| 원칙 | 어디에 | 끄면 생기는 일 |
|---|---|---|
| 인용 무결성 (`require_evidence`) | 협업 노드 | 여느 AI 챗봇과 같아짐 |
| 버전 승급 규율 | 정의 YAML | 실행 이력 재현 불가 |
| 부작용 등급 (L0~L3) | 도구 정의 | 예상 못 한 외부 영향 발생 |
| 구조=계약, 텍스트=증거 | 파서 | 프롬프트 인젝션에 무방비 |
